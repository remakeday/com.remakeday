# 게임 리뷰 검증 결과

검증일: 2026-09-08 · 대상: [review.md](review.md), 현재 소스, 실행 중인 로컬 서비스, 기존 DB 기록

리뷰의 낮은 통과율과 여러 구현 결함은 재현됐다. 다만 **“채점기 문제가 아니다”, “44.8점이 구조적 상한”, “방송이 전혀 표시되지 않는다”는 결론은 현재 근거로 유지할 수 없다.** 입력 정규화·의미 판정·정보 전달을 함께 검증하고 고쳐야 한다.

## 1. 검증 범위와 한계

- DB는 `REPEATABLE READ, READ ONLY` 트랜잭션으로 집계했다. 제출 65건의 저장된 판정을 사용해 산식을 다시 계산했다. 기존 제출을 현재 LLM으로 모두 재채점한 것은 아니다.
- 실행 중인 백엔드 `/health`, 프론트 `/play` 응답을 확인했다. 현재 핵심 LLM은 Ollama `gemma3:12b`다.
- 현재 프롬프트와 모델로 정규화 1건, 명제 판정 5건을 직접 호출했다. 게임 DB에 저장하지 않은 진단 입력이며, 정답을 모르는 플레이어의 발견 가능성을 측정한 실험은 아니다.
- Playwright와 실제 Chrome으로 프론트를 검증했다. **API 응답을 테스트 데이터로 대체했다.** 화면 동작은 확인했지만 실제 NPC·DB까지 연결한 5회차 종단간 플레이는 수행하지 않았다.
- 기존 채점 관련 백엔드 테스트 23개와 프론트 TypeScript 검사가 통과했다. 전체 테스트 스위트와 성능·보안 검증은 범위 밖이다.
- 게임 소스와 게임 DB는 변경하지 않았다. 이 문서와 검증 자료만 프로젝트에 추가했다.

## 3. 수정 우선순위가 높은 실제 문제

### 3.1 실패 시 힌트 경로가 닫혀 있다

[`cookie_rules.select_cookie`](../backend/apps/engine/domain/entities/cookie_rules.py)는 50점 미만이면 `None`을 반환한다. identity 힌트는 다른 세 칸이 모두 100점이어야 후보가 된다.

더 중요한 점은 [`NightInteractor.submit`](../backend/apps/engine/app/use_cases/night_interactor.py)의 호출 위치다. `_pick_cookie` 자체가 성공 종료 분기에만 있다. 실패 후 화면도 성공 화면의 쿠키 표시 경로로 진입하지 않는다. **조건문 한 줄을 반전하는 것으로는 실패한 플레이어에게 힌트가 전달되지 않는다.** 실패 제출 응답, 화면 전환, 다음 회차의 힌트 소비까지 함께 설계해야 한다. 쿠키 A/B 설정도 결과에 영향을 준다.

### 3.2 정규화가 원래 답의 의미를 손실시킨다

현재 Normalizer에 다음 내용이 포함된 입력을 보냈다.

> 채연은 열이 나지만 이송될까 봐 숨긴다.

출력은 `채연은 열이 나지만 숨긴다.`였다. 다른 출력 주장에도 이송을 두려워한다는 동기가 보존되지 않았다. 동일 원문을 직접 판정기에 넣으면 motive-1은 `confirmed`였다. **사용자가 맞게 쓴 내용을 채점 이전에 잃을 수 있는 경로가 실제로 재현됐다.**

정규화 실패 시 폴백은 자유서술만 분할하고 선택한 노트를 무시한다. 따라서 노트만 선택한 상태에서 정규화가 실패하면 빈 주장이 된다. 다만 과거 DB에서 Normalizer 하네스 실패 기록은 발견하지 못했으므로, 과거 0점들을 이 폴백 탓이라고 단정할 수는 없다.

### 3.3 판정기의 의미 오판도 검증 대상이다

현재 운영 판정과 같은 시스템 프롬프트, temperature 0, 인덱스 검사를 사용한 진단 결과다.

| 정답 명제 | 후보 답 | 결과 |
|---|---|---|
| 채연은 이송될까 봐 숨겼다 | 채연은 열이 나지만 이송될까 봐 숨긴다. | confirmed |
| 저녁까지 퍼졌다 | 채연의 열병이 저녁까지 다른 사람에게 퍼졌다. | confirmed |
| 이상자 3명 넘어 구역 폐쇄 | 아픈 사람이 셋을 넘으면 구역이 폐쇄된다. | confirmed |
| 그 두려움은 사실이다 | 이송된 사람은 돌아오지 않는다. 채연이 이송될까 봐 두려워한 것은 사실이었다. | confirmed |
| 관리자는 옆 구역을 지키려 한다 | 관리자는 열병이 옆 구역으로 퍼지는 걸 막으려고 우리 구역을 폐쇄했다. | **none** |

마지막 후보는 캘리브레이션에도 쓰이는 정답형 문장이다. 의미상 맞는 답을 놓치는 사례가 현재 호출에서 발생했다. 반대로 과거 confirmed가 없던 명제 일부는 현재 명시적인 답으로 confirmed가 나온다. **“해당 명제는 판정 규칙상 무조건 none”, “판정기를 마지막에 고쳐도 된다” 모두 근거가 부족하다.**

각 입력 1회 결과이므로 오판율이나 항상 재현되는 동작으로 일반화하지 않는다. [전체 입력·출력](review-verification/2026-09-08/llm-probe.jsonl)

### 3.4 폐기와 빈 제출을 플레이어가 이해하기 어렵다

날조 필터의 비교 대상은 **자유서술 + 선택한 노트**다. 사용자가 자유서술에 직접 적은 새로운 추론을, 게임 단서에 없다는 이유만으로 금지하는 필터는 아니다. 반면 정규화가 도입한 표현을 어휘 검사로 삭제할 수 있고, 삭제 이유를 draft 응답으로 전달하지 않는다.

실제 프론트에서 다음을 확인했다.

- 노트만 선택해도 자유서술 없이 정리를 진행할 수 있다.
- 최초 입력 화면에서 8개 상한과 전체 채점 항목을 안내하지 않는다. 8개 안내는 **정리 후 확인 화면, 최종 채점 전**에 표시된다.
- draft가 빈 주장 목록을 반환해도 “맞아, 제출한다” 버튼이 활성화되고 제출 요청이 발생한다.

빈 목록은 실제 DB에도 있지만 브라우저에서는 해당 응답을 주입해 UI를 검사했다. [모바일 입력 화면](review-verification/2026-09-08/night-mobile.png), [빈 목록 확인 화면](review-verification/2026-09-08/empty-confirm.png)

### 3.5 명제·관측 정보·실제 규칙의 정합성을 맞춰야 한다

`cause-5`는 “3명 넘어”라고 쓰여 있지만 [`world_outcome`](../backend/apps/engine/domain/entities/scoring_rules.py)은 **3명 이상**에서 폐쇄한다. 리뷰가 제안한 “셋을 넘으면”으로 문장만 다듬어도 이 불일치는 남는다.

원인 체인 입력의 이벤트 허용 목록은 `DEATH`와 `LOOP_END`를 제외한다. 밤의 결과를 명시적으로 제공하지 않는 현재 경로는 후속 추론에 필요한 정보 손실 가능성을 만든다.

정보 전달은 보완할 필요가 있으나 “정보원이 전혀 없다”는 단정은 피해야 한다. NPC 프롬프트의 `surface_summary`나 persona를 통한 간접 전달 경로가 있으며, 그 정보가 실제 대화에서 얼마나 안정적으로 발견되는지는 별도 플레이 검증이 필요하다.

### 3.6 Planner와 한국어 하네스 문제

81개 loop 모두 Planner 폴백이 기록됐다. 재시도까지 합친 위반 항목은 `혼자 있다` 154개, `소등` 80개, `말한다` 8개, `채연을 지켜본다` 1개다. `unknown_person`의 `중이`, `지켜`, `일이` 오탐도 기록에서 확인했다.

다만 정적 비트 서술과 파편 적립은 Planner 성공과 별개로 실행된다. **“Planner가 폴백이면 새로 넣은 정보원이 세계에 나타나지 않는다”는 설명은 정적 파편·서술에는 적용되지 않는다.** 허용 어휘를 늘리기 전에 행동 스키마와 생성 프롬프트의 일치 여부를 확인해야 한다.

## 5. 산식 시뮬레이션 재현

65건의 **저장된 판정은 유지**하고 산식만 바꾼 결과로, 리뷰의 표 전체가 재현됐다.

|---|---:|---:|
| 현행 | 20.3 | 2/65, 3.1% |
| A: 만점 임계 0.6 | 25.8 | 7/65, 10.8% |
| B: partial 가중 0.7 | 25.2 | 5/65, 7.7% |

다음 수정은 아래 순서로 검증하는 것이 적절하다. 이번에는 수정하지 않았다.

1. **입력 보존·판정 정확성:** 실제 원문 → 정규화 → 필터 → 판정을 한 묶음으로 저장한다. 동기 누락과 의미상 맞는 답의 none 사례를 회귀 세트에 넣고, 오답·부분 정답·정답을 사람이 구분한다. 높은 점수의 제출이라는 이유만으로 정답 라벨을 주지 않는다.
2. **실패 후 학습 경로:** 실패 응답에서 힌트가 실제로 표시되고 다음 회차에서 사용할 수 있는지, 빈 주장에는 복구 경로가 있는지 브라우저와 실제 API를 연결해 검사한다.
3. **관측 가능한 근거:** 각 명제에 어느 비트·파편·대화·전날 결과가 근거인지 대응표를 만든다. 정답을 숨긴 별도 플레이 세션에서 그 근거를 실제로 발견하고 메모·주장으로 옮기는지 확인한다.
4. **세계 실행 품질:** Planner 유효 출력과 한국어 이름 검사 오탐을 별도 측정한다. 정적 파편 표시와 NPC의 동적 행동 성공률을 구분한다.
5. **난이도 조정:** 위 문제를 고친 뒤 동일 제출 재채점과 새로운 플레이 결과를 각각 비교한다. 그 근거로 명제 수, 슬롯 수, 칸 가중치, 통과선을 조정한다.

브라우저 자동화만으로는 이 게임의 핵심 문제를 검증할 수 없다. **DB 재현 분석 + LLM 의미 평가 + 브라우저 흐름 검사 + 정답을 모르는 실제 플레이**가 함께 필요하다. 이번 검증은 앞의 세 가지에 대한 초기 근거를 확보했다.
